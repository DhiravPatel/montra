# Montra — Authorization Matrix

Authorization is enforced by the Go API on every request (never by
clients) and again by PostgreSQL RLS (`docs/RLS_POLICY_MATRIX.md`).

## Layers

1. **Session.**
   - Protected operations need a valid access token: a bearer token for
     mobile, or an HttpOnly cookie for web, which also needs the
     `X-CSRF-Token` header on unsafe methods.
   - Public operations are an explicit allowlist that
     `internal/app/authz_inventory_test.go` enforces: registration and
     sign-in flows, legal versions, currencies, signed file downloads,
     signed unsubscribe links and provider webhooks.
2. **Operation.**
   - Some operations need a recent re-authentication: two-step setup,
     disable and recovery codes, data export, deactivation and deletion.
     A password change instead requires the current password in the
     request.
   - Platform-staff operations need a staff role (`support`, `admin`).
   - Each operation has a rate-limit policy.
3. **Object.** Services load the target as the caller (RLS-scoped
   transaction) and check ownership or membership before any change.
   Objects the caller cannot see answer 404, never 403, so existence is
   not disclosed.
4. **Database.** RLS policies and guard triggers make a missed check fail
   closed.

## Object rules by module

| Module | Who may read | Who may change | Notes |
|---|---|---|---|
| Accounts, transactions, categories, tags, merchants, payment methods | owner | owner | household members read accounts explicitly shared with the household, and their transactions (read-only); group-linked personal records stay owner-only (ADR-036) |
| Budgets, goals | owner; collaborators by role | owner/editor (budgets), owner (goals); contributors record contributions | collaborator visibility follows the share settings |
| Recurring, bills, subscriptions, planning calendar | owner | owner | group recurring rules: group members per group role |
| Receipts, imports, reconciliation, files | owner | owner | files open only through signed, expiring URLs after an ownership check; group files to group members |
| Reports, analytics, exports | owner | owner | the worker builds reports as the owner through the RLS-enforcing pool |
| Groups, expenses, settlements | active members | members (expenses, comments, disputes); admins (settings, members, invitations); parties (settlement confirm/dispute) | other members' personal records are changed only by the worker |
| Social graph | you and the other party | you | discovery returns minimal profiles of opted-in users; blocks hide both ways |
| Communities, posts, challenges | per visibility (public, private members, invite-only) | authors (own content); moderators (community content and membership); staff (platform sanctions) | guard triggers stop self-promotion and self-unbanning |
| Moderation | moderators of the community; staff | moderators; staff | reporters see their own reports and appeals |
| AI, insights | owner | owner | AI tools run as the caller and are read-only |
| Notifications, preferences, push endpoints | owner | owner | security/account categories cannot be disabled |
| Integrations | owner | owner | OAuth state bound to the user; tokens never returned; webhooks verified by provider signature |
| Privacy (export, deletion, consents) | owner | owner, with recent re-auth for export and deletion | deletion has a grace period and is executed by the worker |
